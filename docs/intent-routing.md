# 意图识别测试页：开发与评测

状态：规则与生成式分类已接入测试页，embedding 对照正在试做。本文负责 `/devtools/intent-routing` 的识别对照与评测；同一页面的完整医疗咨询试跑见 [medical-consultation-routing.md](./medical-consultation-routing.md) 第 6.3 节。正式路由、医疗 agent 和发布门槛也以该文档为准。

## 两份计划的执行顺序

1. 先按本文第 2—7 节完成识别实验：核对现有实现，补齐规则、生成式模型和 embedding 的单句对照、批量评测、错例及运行配置记录。以本文第 5、7 节验收；不要把实验结果接入正式聊天。
2. 再按 [医疗咨询总设计](./medical-consultation-routing.md) 第 7、8 节核验评测基线，实施正式逐轮路由、医疗回答及用户配置。是否启用医疗生成由独立验收决定，不能以本页开发集成绩代替。
3. 正式路由和回答逻辑可复用后，按总设计第 6.3 节及阶段 D 扩展**同一个页面**：增加多轮输入、完整试跑、逐步结果和错例回填。保留本文的识别对照能力；完整试跑不得写入正式会话或触发外部副作用。

开发时分别核对两份文档对应阶段的完成标准。若页面要求与正式路由行为冲突，以总设计的运行契约为准，并在测试页展示实际路由结果。

## 1. 范围与当前行为

测试页位于 `apps/stage-web/src/pages/devtools/intent-routing.vue`，只在开发环境提供。它直接调用分类器，不写聊天会话，也不改变正式回复。页面按第 9.2 节改成**五个页签**，共用输入在页签上方：**规则** / **生成式模型**（只有这里能编辑分类提示词草稿）/ **Embedding**（服务、参考向量、阈值与近邻）/ **三方对照**（同一份输入一次跑三种方法，三列并列，每列显示自己实际收到的文本、失败与耗时）/ **完整试跑**（正式路由 + 咨询回答）。配置摘要与共用输入（当前消息 + 上文）在页签之上，批量评测、结果追溯在页签之下，本次记录作为附录。三方对照的每一列独立失败：一边连不上不掩盖另一边；输入或配置改变后，旧结果会出现「已经变了，重新跑一次」的提示。选 Embedding 页签时「只测识别」走向量单句、「跑测试集」走向量批量，两条路径都不调用聊天模型。完整试跑调用 `previewMedicalTurn()`，走正式路由与提示词组装，用页面“上文”做多轮输入，读页面提示词草稿，结果只留在页面上。测试页的模型列取当前聊天 Provider 与模型；只有选中 DeepSeek 时，这列才调用 DeepSeek。

正式聊天与测试页分开：`VITE_MEDICAL_GENERATION` 关闭时，规则决定医疗固定回复、急症指引或普通聊天；开启时，急症规则先行，其余消息由当前聊天模型分类。测试页的 embedding 结果目前不参与 `chat.ts`、`routeMedicalTurn()`、角色卡设置或聊天工具调用。

| 测试方式 | 当前职责 | 是否改变正式聊天 |
| --- | --- | --- |
| `rules` | 运行关键词和急症规则 | 否 |
| `model` | 请求当前聊天模型输出分类 JSON | 否 |
| `compare` | 并列比较规则与生成式分类 | 否 |
| `embedding` | 用参考向量判断医疗、闲聊或不确定；与上面三项同一排按钮，不调用聊天模型 | 否 |

原阶段二的目标是比较规则与 DeepSeek。现在增加 embedding，是为了测试它能否覆盖关键词规则遗漏的表述，并观察它与生成式分类的差异。三种结果都需要保留，不能把实验阈值直接写入正式路由。

## 2. 分类契约与代码位置

`packages/stage-ui/src/libs/intent/contract.ts` 拥有 `IntentDecision`：`decision` 为 `medical | chat`，另有 `scene`、`evidenceCodes`、`source` 和 `classifierVersion`。规则结果的 `source` 为 `rule`，生成式模型有效结果为 `model`，请求失败或输出无效为 `fallback`。评测时，`fallback` 不是一次有效的医疗判断，不能按返回的保守标签计为命中。

| 位置 | 职责 |
| --- | --- |
| `packages/stage-ui/src/libs/intent/classify-rules.ts` | 规则分类和急症词匹配 |
| `packages/stage-ui/src/libs/intent/classify-model.ts` | 生成式分类请求、JSON 解析和失败原因 |
| `packages/stage-ui/src/libs/intent/classify-embedding.ts` | 请求向量、计算相似度、聚合邻居分数和不确定判定 |
| `packages/stage-ui/src/libs/intent/classify.ts` | 原有 `rules`、`model`、`compare` 模式 |
| `packages/stage-ui/src/libs/intent/evaluate.ts` 与 `fixtures/` | 标注样本、分组、召回与误判统计 |
| `packages/stage-ui/scripts/dev-local-embeddings.mjs` | 开发环境的本地向量服务 |
| `apps/stage-web/src/pages/devtools/intent-routing.vue` | 参数输入、单句对照、批量报告和错例展示 |

生成式分类使用当前聊天 Provider 的 `chat(model)`，关闭 reasoning，以非流式方式请求一个 JSON 对象。分类提示词可在测试页试改；草稿只供试验，不能直接变成正式配置。失败要显示原因并单列，不把 JSON 或失败标签当作用户回复。

Embedding 使用独立的端点与模型，不复用 `activeModel`。当前工作区通过 `@xsai/embed` 请求兼容 OpenAI 的向量接口。原聊天 Provider 的配置不能证明它提供 embedding 服务。向量分类只输出类别、相似度和不确定状态；它不负责医疗回答，也不生成 `scene`。

## 3. Embedding 模型与本地试跑

目前页面默认连接 `http://127.0.0.1:5178/v1`，默认模型为 `Xenova/bge-small-zh-v1.5`。在 `packages/stage-ui` 下运行：

```bash
node scripts/dev-local-embeddings.mjs
```

本地服务首次请求需要下载模型；脚本支持 `HF_MIRROR` 和 `TRANSFORMERS_CACHE`。模型文件默认缓存到 `packages/stage-ui/.tmp/transformers`。页面的服务检测、向量构建和单句测试要分别报告连接、加载和请求错误，不能用模拟结果冒充真实效果。

| 候选 | 用途 | 试验前核对 |
| --- | --- | --- |
| `Xenova/bge-small-zh-v1.5` | 当前本地页面基线 | 端点是否运行、向量维度和首次加载时间 |
| Qwen3-Embedding-0.6B、BGE-M3 | 后续候选 | 实际接口、输入指令、维度、版本和本机资源 |
| 经评估的云端 embedding 服务 | 比较远端效果、延迟和费用 | API 兼容性、请求上限、医疗文本处理要求 |

云端试验的端点、模型和密钥可分别由 `VITE_MEDICAL_EMBEDDING_BASE_URL`、`VITE_MEDICAL_EMBEDDING_MODEL`、`VITE_MEDICAL_EMBEDDING_API_KEY` 提供。密钥不应存进页面 `localStorage`。但 `VITE_` 变量会打包到浏览器，不能视为保密方案；需要隐藏密钥时，应另设计服务端代理。最终模型和服务须在可比较的样本上确定。

## 4. 参考集与判定

参考集来自带 `medical | chat` 人工标签的开发样本。保留 `hospital-process`、`short-reply`、`asr-noise` 等分组，以便定位边界错例。当前 92 条开发样本可用于调试，不能替代未参与调参的验收集。缺乏上文的短句要先复核标签。

构建时将样本批量转成向量，保存样本 ID、标签及向量。对查询向量分别取医疗与闲聊中最相近的若干条，计算类别分数和分差；分差低于页面的试验阈值时输出“不确定”。一个最近邻或一个固定的余弦阈值不足以决定路由。“医院停车”与“复查挂哪个科”这类句子必须作为边界样本观察。

单句与批量评测的输入格式应一致，并保留必要上文的角色和顺序。若模型需要不同的查询与参考前缀，须记录前缀版本。端点、模型、样本版本或输入模板变化后，参考向量必须失效并重建。维度不一致、空向量和非有限分数都应给出错误或“不确定”，不能产生可靠分类的假象。初期样本量较小，可在内存中精确计算余弦相似度，无需向量数据库。

开发集内部评分时，查询样本不得给自己投票；同义改写或近重复句也需隔离，否则结果可能虚高。独立验收集的原文、向量和标签不能用于参考集、阈值选择或模型选择。分数、阈值和最近邻样本 ID 可用于诊断；持久化报告与日志不保存用户医疗正文或向量。

## 5. 页面交互与验收

| 操作 | 页面展示 | 验收要求 |
| --- | --- | --- |
| 服务检测与构建参考集 | 端点、模型、参考条数、状态、错误和耗时 | 失败不保留半成品；配置变化后旧向量不可继续使用 |
| 单句对照 | 规则、当前生成式模型与 embedding 三列；医学分数、闲聊分数、分差、最近邻和耗时 | 每列注明“未运行”或失败；单独点 embedding 不调用聊天模型或写会话 |
| 批量评测 | 医疗召回、闲聊误判、不确定率、失败率、分母、耗时和逐条错例 | 三方使用相同标注集；失败与不确定不计为正确 |
| 阈值试验 | 调整分差阈值后的样本变化与指标 | 仅改变页面试验结果，不修改正式路由 |

工作区已有独立的 Embedding 对照区域、参考向量构建、单句测试、批量报告、服务检测和阈值重算。现有批量逻辑排除样本自身及相似度达到当前去重阈值的近重复项。页面应显示实际发送的上文格式；规则、生成式模型和 embedding 的输入契约不完全相同，不应把三列分数说成完全同条件的模型排名。

对每次运行记录样本集版本、参考集身份、端点和模型、向量维度、输入模板、邻居数、阈值、生成式提示词版本以及运行环境。任一项变化后，旧报告标为不可直接比较。若服务没有可靠模型版本，保存具体部署标识并在升级后重建向量、重跑评测。

## 7. 开发顺序与检查

1. 固定一个可用的向量端点、模型与开发样本版本；核对向量数量和维度。
2. 固定参考集身份和输入模板；验证配置变化、失败及取消后不会留下旧结果。
3. 对同一句和同一标注集展示规则、生成式与 embedding 的结果及逐条错例。
4. 只用开发集调整邻居数与阈值；用未参与调参的样本重新验收。

单元测试用模拟向量和模拟模型响应，覆盖同分、低分、零向量、维度不一致、超时、上下文追问、转题、去重和计分。真实服务测试只使用合成或已脱敏样本。运行相关 Vitest、受影响包的 typecheck 和仓库 lint；评测页的启动和页面交互另做人工核验。

## 8. 后续：是否接入正式路由

本节仅记录候选流程，当前测试页不会执行：

```text
用户消息入队
  → 急症规则命中：立即给急诊指引
  → embedding 明确判为医疗或闲聊：作为候选分支
  → embedding 不确定或失败：由生成式分类器判断
  → 两者都无法判断：安全兜底
```

急症规则必须先于模型运行。Embedding“不确定”不是有效的 `chat` 或 `medical`；若将来增加自动转交，应分别统计 embedding 失败、生成式失败和最终轮次失败。不能把失败回退标签计为模型命中。正式策略由部署配置控制，不能由测试页阈值、角色卡或普通用户设置直接改变。

是否接入正式路由，按 [医疗咨询总设计](./medical-consultation-routing.md) 第 7 节的发布门槛决定：医疗召回 ≥95%、闲聊误判 ≤5%、逐轮分类失败率 ≤1%、人工复核急症集全部命中、分类 P95 ≤2 秒。独立验收集至少 300 条，其中至少 150 条医疗、100 条闲聊，并覆盖短句、就医流程和 ASR 错字。报告同时给出不确定率、生成式转交比例、两类请求的失败率、P50/P95 和每轮成本。未达标时保持当前固定医疗回复与部署开关策略。

## 9. 下一步：统一对照与评测闭环（待开发）

本节承接现有页面，不覆盖第 1—8 节的分类契约和正式路由门槛。当前页面已有单句分类、规则与生成式模型对比、独立的 Embedding 区、批量报告，以及完整医疗咨询试跑。以下工作分成两个交付阶段：先让三种分类方法的结果易于比较，再增加样本管理、标注和历史报告。完整咨询试跑继续作为测试台上的独立操作，不计入分类器三方对照。

### 9.1 为什么要重构当前页面

现有功能可以单独使用，但一次评测要在不同区域操作和阅读结果。优先重构页面交互、结果组织和运行记录，不重写已存在的规则、生成式分类器或向量相似度算法。

| 当前表现 | 给评测带来的问题 | 重构方向 |
| --- | --- | --- |
| 顶部 `rules`、`model`、`compare` 只组织规则与生成式模型；Embedding 在更靠后的独立区域 | 同一句需要分别点击和滚动，不能一眼判断三方是否一致 | 共用输入，按方法切换页签；在「三方对照」页签集中展示三列结果 |
| 规则／生成式报告和 Embedding 报告分别运行、分别展示 | 指标和逐条错例难以按同一批样本比较 | 统一逐条结果及统计口径；每列保留自身失败、不确定和耗时 |
| 输入、上文、模型、提示词和阈值可在运行后继续变化 | 旧结果可能看起来仍属于当前输入或配置 | 每次结果绑定输入与配置快照；变化后明确失效或重新计分 |
| 分类对照、Embedding 服务配置、批量表格和完整咨询试跑都在一条长页面 | 测试者难以区分「分类准确率」与「最终回答是否合适」 | 测试台突出分类对照；完整试跑单列为路由与回答检查；样本和报告迁到二级页面 |

重构时先整理页面内的输入、运行状态和结果呈现，再拆分有独立职责的页面或组件。分类、计分和正式路由仍由各自现有模块负责；页面不复制业务判定。旧的 `compare` 按钮可迁移为「三方对照」页签的运行操作，但不能让未运行的 Embedding 看起来已参与结论。三列并排不代表三种方法收到完全相同的输入：页面须展示实际输入契约，并在报告中记录差异。

### 9.2 页面结构与入口

侧边栏保留一个「意图评测」入口。在该入口内使用带独立地址的二级导航，避免把所有功能继续堆在一个长页面里。三个页面共享当前样本集版本和运行配置摘要：

| 二级页面 | 负责的操作 | 首批开发范围 |
| --- | --- | --- |
| 测试台：`/devtools/intent-routing` | 共用单句与上文输入；按页签测试规则、当前生成式模型、Embedding，或查看三方对照与完整咨询试跑 | 先重排现有功能；每个页签只展示自己的设置与结果 |
| 样本集：`/devtools/intent-routing/datasets` | 查看、录入、导入、分组、标注与复核样本 | 第二阶段；标注放在样本详情中，不单建侧边栏入口 |
| 运行与报告：`/devtools/intent-routing/runs` | 选择固定版本批量测试，查看进度、统计、错例及历史运行 | 第二阶段；错例可带上文返回测试台或样本详情 |

路由仅表示产品信息结构；实现时核对现有文件路由的生成规则，不因本节的地址示例另建一套 Devtools 入口。

进入「意图评测」时，从数据库读取最近一次已保存的批量运行，在测试台顶部展示结果摘要、运行时间、测试集和三种方法的状态；点摘要进入完整报告。若当前样本或配置已变化，摘要保留但标明「历史结果，需重新运行」。没有记录时显示空状态，不自动请求模型。进入「运行与报告」默认打开最近一次报告，并可切换历史运行。当前单句测试记录只留在页面会话中；是否需要单独保存单句历史，待内测使用后决定。

测试台内使用 Tab 组件切换功能，不把每种分类方法做成侧边栏菜单。共用输入放在页签上方；各页签只放本功能的操作、设置和结果：

| 测试台页签 | 专属内容 |
| --- | --- |
| 规则 | 规则判定、命中依据和耗时；不展示模型提示词或 Embedding 服务配置 |
| 生成式模型 | 当前 Provider／模型、分类提示词草稿、模型输出、失败原因和耗时；只有此处编辑分类提示词 |
| Embedding | 服务状态、端点／模型、参考向量、分差阈值、近邻和耗时；不展示生成式提示词 |
| 三方对照 | 用同一份输入查看或运行三种方法；并列显示判定、失败／不确定及实际输入差异；不在这里编辑各方法的专属配置 |
| 完整试跑 | 独立展示识别、正式路由和咨询回答；不把回答质量算进分类准确率 |

切换页签不修改输入或抹掉已完成的运行。输入或相关配置变化后，受影响的旧结果标为过期；返回「三方对照」时不能把旧列当成新判断。页签仅组织测试台内部功能；样本集和运行报告仍是上表的二级页面。

「三方对照」页签打开时先展示与当前输入、上文和配置快照匹配的已有结果，不因切换页签自动调用付费模型。需要新结果时，由用户点击「运行三方对照」；运行前显示预计请求数，运行中展示各列状态。单独方法页签产生的结果只有快照完全一致时才能复用。无法运行的一列单独标记失败或未运行，不阻止其他列完成。

### 9.3 先完成三方对照

测试台只保留一份当前输入：当前消息、按角色和顺序记录的必要上文，以及本次配置。在「三方对照」页签运行后，集中展示规则、当前生成式模型、Embedding 三列。每列显示「医疗／闲聊／不确定／失败／未运行」、耗时和可解释信息；模型回退不能显示为有效的医疗命中。生成式列使用实际选中的 Provider 和模型名，不固定写成 DeepSeek。

规则、生成式模型和 Embedding 的输入能力不同，页面要展示各列实际收到的文本与上文。任一输入、提示词、端点、模型或阈值变化后，旧结果不得继续显示为同一次可比较的结果。Embedding 仍需构建参考向量；若无法连接服务，该列显示失败，其余两列可独立完成。完整咨询试跑显示路由与回答，不混入三列分类准确率。

批量结果统一为「一行样本，三列判定」，可按分组、标准答案、三方分歧、医疗漏判、闲聊误判、不确定和失败筛选。统计并排显示三方的医疗召回、闲聊误判、失败率、不确定率、分母和耗时；没有运行的一列不显示零分。第一阶段沿用现有开发样本，完成同屏对照、结果失效和统一错例筛选，不开放样本编辑。

### 9.4 再建立样本与标注闭环

```text
收集合成或脱敏样本 → 人工标注与复核 → 选择当前测试集
  → 选择方法和配置运行 → 查看统计、分歧与错例
  → 返回测试台复现，或返回样本详情修正 → 再运行
```

每条样本至少有稳定 ID、当前消息、必要上文及其角色、分组、人工标签、标注状态和来源说明。内测期间，所有能使用开发工具的人员都可直接编辑标签和复核样本；不增加复核角色、修改人日志或手动冻结流程。模型输出可帮助定位待复核样本，不能自动写成标准答案。批量导入先核对格式、重复样本和缺失上文，再由人确认入库。正式发布验收前再确定是否需要更严格的复核规则。

开发集可用于调提示词、参考样本和阈值；独立验收集只用于最终检验。Embedding 的参考集不得包含验收查询，也不能让开发集中的查询给自己或近重复句投票。当前 92 条样本只作为开发集起点，不因加入管理页面而自动成为独立验收集。参考集内容、向量模型或输入模板变化后重建参考向量；测试集内容或标签变化后重跑评测，并将相关旧结果标记为不可直接比较。

一次批量运行记录参考集身份、模型与端点、分类提示词摘要、输入模板、邻居数和阈值。报告保存样本 ID、逐条判定、当次统计、指标分母、失败原因、开始时间及运行状态；不额外复制样本正文或人工标签。取消或失败时明确报告是否完整。内测期间可直接修改测试集再运行；旧报告只表示当时算出的结果，样本改动后不保证能按旧报告复现，页面提示重新运行。持久化内容只使用合成或脱敏文本；不记录密钥或用户原始医疗消息。

样本、人工标签、逐条运行结果和报告均存数据库，由应用接口读写；浏览器本地存储不作为这些数据的权威来源。运行期间的临时进度可留在页面状态中，刷新后仍须从数据库恢复已保存的运行状态。数据库类型、部署位置和接口契约在实施前结合现有项目后端确定，本节不指定新依赖。

服务端落点（已实现，待测试）：`server/apps/api` 挂载 `/api/v1/intent-eval`，沿用现有资源 API 的形状。

| 路由 | 作用 |
| --- | --- |
| `GET /samples`、`POST /samples` | 列出与新建样本 |
| `POST /samples/import` | 批量导入（单条请求上限 500 条，一条坏行整批拒绝） |
| `PATCH /samples/:id`、`DELETE /samples/:id` | 改标签或复核状态；删除是软删除，已跑过的运行保留自己的快照 |
| `GET /runs?limit=`、`GET /runs/:id` | 列出与读取运行（默认 20 条，最多 100） |
| `POST /runs` | 开一次运行，固定样本集版本、模式、`configKey`、模型、提示词摘要与向量身份 |
| `PATCH /runs/:id` | 上报进度与结果；进入终态时自动写 `finishedAt` |

表为 `intent_samples` 与 `intent_runs`（`server/apps/api/src/schemas/intent-eval.ts`），迁移文件 `drizzle/0029_*.sql`。所有读写按登录用户过滤，别人的资源返回 404 而不是 403，避免用 id 探测存在性；存储的 `metrics` 与 `cases` JSON 在读取时用 Valibot 校验，旧版本写入的形状不会被当作当前结果返回。账户删除已接入：`app.ts` 注册 `intent-eval` 的 `softDelete`，在一个事务里软删两张表。

页面接入（已实现，待测试）：批量评测优先读服务端样本，读不到（未登录或服务不可用）就退回内置 92 条，页面写明当前来源；「把内置样本导入服务端」一次写入整套开发样本；每次跑完测试集自动写一条运行记录（`POST /runs` + `PATCH /runs/:id`），写入失败只在页面上提示、不影响已显示的数字；「运行历史」列出最近 20 次运行的状况、模式、条数、配置与起止时间。挂载时自动跑的那次评测不写历史，避免每刷新一次页面就多一条。前端客户端在 `packages/stage-ui/src/libs/intent/api.ts`。

样本集页面（已实现，待测试）：`apps/stage-web/src/pages/devtools/intent-routing/datasets.vue`，地址 `/devtools/intent-routing/datasets`，从测试台顶部链接进入。它支持单条新增（消息、上文、分组、标答、来源）、JSON 批量导入（数组，最多 500 条，服务端逐行校验）、以及每行「改标答 / 标记已复核 / 删除」；表格同时显示分组、上文、来源与复核状态。删除是软删除，已跑过的运行保留自己的快照，因此这里改标签不会改写历史报告。

### 9.5 开发与验收顺序

| 顺序 | 交付物 | 验收点 | 状态 |
| --- | --- | --- | --- |
| 1 | 测试台方法页签与三方对照 | 规则页签不显示提示词，生成式页签才可编辑提示词；同一输入可在对照页签看到三列结果；改输入后旧列不再冒充新结果 | 待测试 |
| 2 | 统一的逐条批量结果 | 同一批样本可筛出三方分歧和错例；指标分母、输入差异及 Embedding 参考集清楚可见 | 待测试 |
| 3 | 样本集与人工标注 | 可录入、导入、编辑标签和复核；不要求手动冻结或记录修改人 | 待测试（服务端 CRUD + 样本集页面） |
| 4 | 运行历史与错例回流 | 最新报告的错例可用当前样本回填；修正后重新运行。旧报告保留统计与判定，不承诺复现已修改的样本 | 待测试（错例回流、运行写入、运行历史与详情页面） |
| 5 | 简易评测报告 | 一份可导出的文档，列出三方指标与分母、分组统计、错例摘要，并逐项对照发布门槛给出结论；样本数不足或任一门槛未达时明确写出限制 | 待测试 |

第 1 项的当前实现（待测试）：页签用 `SelectTab`，`tab` 是唯一的方法控件，`mode` 由 `watch(tab)` 同步，所以一次运行不会被标成页签没显示的方法；共用输入在页签上方；分类提示词草稿只在生成式页签出现；三方对照用 `runThreeWay()` 并发跑生成式与向量，各自保留失败，规则同步给出结果；`composeClassifierUserText()` 让页面显示与分类器实际发送完全一致的文本；`threeWayStale` 比对消息、上文、模型、提示词摘要与阈值，任一变化即提示旧结果不可比。

第 2 项的当前实现（待测试）：`EvaluationReport` 新增 `cases`，保留每个样本的两侧判定，因此三列可以在**同一次运行**里按样本 ID 合并；页面把报告与 `embedVotes` 合成 `batchRows`，Embedding 的判定在读取时按当前阈值计算（改阈值不重新请求）；筛选按钮覆盖全部 / 三方分歧 / 医疗漏判 / 闲聊误判 / 不确定 / 失败；指标表按方法并排给出召回、误判、失败率、不确定数与**分母**；表中每行显示标答、三列判定、分差与是否分歧，并带出该样本的上文。旧的「两边不一致 / 规则漏判 / 模型失败」三张表保留为「分侧明细」。

第 4 项的运行历史部分（已实现，待测试）：`apps/stage-web/src/pages/devtools/intent-routing/runs.vue`，地址 `/devtools/intent-routing/runs`。列表可切换最近 20/50/100 次，选中后看到这次运行的配置指纹、提示词摘要、起止时间与提前结束原因，以及三方指标（含分母）与逐条结果；逐条结果支持「全部 / 不一致 / 失败 / 不确定」筛选。页面只读：一份运行是不可变记录，它保存自己的样本快照，因此改样本或改标签都不会改写历史报告。测试台底部与样本集页面各有入口。
第 5 项（简易评测报告）的当前实现（待测试）：`packages/stage-ui/src/libs/intent/report.ts` 的 `buildEvaluationMarkdown()` 把当前表格的数据渲染成 Markdown——三方指标与分母、分组统计、三方不一致的前 10 条、以及逐项对照 §7 门槛（召回 ≥95%、误判 ≤5%、失败率 ≤1%）的 ✅/❌ 与结论句；样本数少于 300 条时自动加一段「只作开发集诊断、不能作为上线依据」。门槛数字集中在该文件的 `releaseGates`，改门槛只改一处。测试台「批量评测」区有「导出报告（Markdown）」按钮和报告预览。P95 耗时与医疗回答人工审核不在报告内，结论句会写明这两项另计。

第 4 项的已实现部分（待测试）：统一表每行有「回填」，把该样本的当前消息与它的上文写回共用输入，并记下来源样本 ID；留在页面上先看识别，再决定是否跑完整试跑。仍未做的是运行历史归档与样本修正，后者依赖第 3 项的样本集。

已确定：样本与报告存数据库，开发工具使用者均可编辑和复核；内测阶段不做修改人日志或手动冻结。建议把独立验收集从测试台的日常单句列表和 Embedding 参考集中排除，仅在「运行与报告」中用于最终批量验收。验收完成后可查看错例；若依据这些错例调参，该批样本须退出独立验收集，不能再作为最终验收依据。是否采用这一验收集展示规则，需在实现样本管理前确认。不预先引入向量数据库或通用标注平台。

### 9.6 样本集管理：内测版实施规格

本节细化第 9.5 节第 3 项。先实现能录入、改标签、选集合并运行的管理页；不加入修改人日志、手动冻结、审批流或通用标注平台。数据库优先复用现有 `server/apps/api` 的 PostgreSQL、Drizzle 和 Hono 接线；开发前须确认本地 `stage-web` 能连到该 API。无后端连接时页面显示不可用原因，不用浏览器本地存储冒充数据库。

当前工作区已有 `server/apps/api/src/routes/intent-eval/`、`services/domain/intent-eval.ts` 和 `schemas/intent-eval.ts`：提供样本增删改查、批量导入和运行记录接口。它们仍按登录用户隔离数据，样本只用 `sampleSetVersion` 区分，没有可命名的样本集；上文是单条 `previous`，标签必须填写，运行记录的 `cases` 保存样本快照。以下表格是下一步目标，不代表这些字段或操作已经实现。开始开发时先核对正在改动的服务端代码，再决定如何在现有接口上扩展，避免新建并行数据模型。

**数据与约束**

| 记录 | 内测版字段 | 规则 |
| --- | --- | --- |
| 样本集 | 稳定 ID、名称、用途 `development` 或 `acceptance` | 名称可改；同一集合中的样本供一次批量运行选择。用途只用于区分开发与验收，不增加角色权限或冻结状态 |
| 样本 | 稳定 ID、所属集合 ID、当前消息、上文、人工标签（`medical`、`chat` 或未标注）、现有分组、复核状态 | 正文不能为空；未标注样本可保存但不能算作正确或错误；复核状态只表示人工确认，不限制谁能修改 |
| 运行关联 | 运行 ID、集合 ID、样本 ID、方法判定与当次统计 | 旧报告不复制样本正文或人工标签；样本被改动或删除后，旧报告标为历史结果，不能用当前标签重算旧准确率 |

上文在存储和接口中按角色及顺序表示为消息数组。导入现有 `fixtures/` 时，把 `previous` 映射为一条 `user` 上文；没有 `previous` 则为空数组。批量评测要读取同一份上文，不能继续只接收一个无角色字符串，也不能静默丢弃 `assistant` 上文。旧的 92 条代码样本只作初始开发数据：「导入内置样本」写入一个开发集合，重复导入按稳定 ID 跳过，不覆盖数据库里已编辑的内容。代码常量在迁移期可继续供旧页面使用；管理页和新批量运行只以数据库数据为准。

**页面操作**

| 区域 | 操作与反馈 |
| --- | --- |
| 集合列表 | 显示名称、用途、样本数、已标注数和最近一次运行入口；可新建、改名、选择集合。空库时引导新建或导入内置样本 |
| 样本列表 | 按关键词、分组、标签和复核状态筛选；每行显示 ID、消息摘要、标签与是否有上文。点一行打开详情，不在长表格内编辑正文 |
| 样本详情 | 编辑当前消息、按顺序编辑上文角色与内容、分组、标签和复核状态；保存后列表立即更新。改标签或正文后提示已有报告需要重跑 |
| 导入 | 首版支持现有样本结构的 JSON；先预览总数、缺字段、重复 ID 和无效标签，再确认写入。整批校验失败不写入半批数据 |
| 删除 | 删除样本或空集合前确认；有历史报告时仍可删除样本，但旧报告只能显示样本 ID 和当时判定。首版不提供恢复功能 |

输入与上文只接收合成或已脱敏内容。相同消息和上文的重复项给出提示，由人决定是否保留；不同标签的近似句不自动合并。模型判定可从报告带入详情供人工参考，但不能自动写入人工标签。内测人员可直接标注和复核，不要求第二人签字。

**接口与边界**

在现有 `intent-eval` 接口上增加集合的列表／创建／改名／删除，以及按集合查询样本；样本的新增／修改／删除和 JSON 导入沿用现有路由并补齐集合归属。首版只有数百条样本，查询可一次返回，再由页面筛选；数据量增长后再加分页。接口校验标签、分组、上文角色、输入长度和集合归属；导入须整批成功或整批失败。前端只通过接口读写，不直接连接数据库。所有能进入开发工具的登录用户可操作复核状态；现有 API 按 `userId` 隔离样本，如需多人共用一个集合，须先明确共享范围并调整查询边界，不可只在前端放开按钮。后端保留现有身份与环境边界，不开放匿名写入；不为此引入新的数据库或表单库。

批量评测从所选数据库集合取**已标注**样本；未标注样本显示数量并跳过，不计入任何指标分母。选定集合后显示将运行的样本数和预计模型请求数，再由用户主动开始。测试台回填使用样本 ID 读取当前内容；样本被删除时给出明确提示。开发集合的正文、上文或标签改变后，重建受影响的 Embedding 参考数据，并提示已有报告不再代表当前集合。验收集是否允许在日常测试台选择，仍按第 9.5 节末尾的待确认建议处理。

**实施顺序与完成标准**

1. 接通现有 API 与数据库，新增集合和样本的存取边界；用接口测试覆盖校验、分页、导入事务和空库。
2. 实现集合列表、样本列表与详情编辑；验证新增、改标签、带角色上文和删除后的页面状态。
3. 提供内置 92 条样本的幂等导入；确认重复导入不覆盖手工修改，也不把它们标作独立验收集。
4. 让批量评测读选中的数据库集合；核对已标注数、指标分母、上文输入和 Embedding 参考集。运行前需明确显示预计请求数。
5. 将最近一次报告与历史报告存数据库；刷新后仍能看到最近结果。样本变动后旧报告显示为历史结果，不再用当前标签重算。
