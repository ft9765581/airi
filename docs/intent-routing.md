# 医学问题分流（意图识别）设计

状态：设计稿，未实现。适用 `apps/stage-web`（线上只有网页版）。

本文档只讲架构。代码怎么写，等架构定下来再谈。

## 1. 目标

只回答一个问题：这句话是不是专业医学问题。是就分流，不是就正常闲聊。

分两个阶段落地，两阶段共用同一个判定。

| 阶段 | 判定为医学问题后做什么 | 需要什么 |
| --- | --- | --- |
| 阶段一 | 回一句固定话术，不调模型。例：「我暂时回答不了医学问题」 | 判定层 + 发送前拦截 |
| 阶段二 | 换一套提示词，并检索知识库 | 判定层 + 上下文注入 + 提示词切换 |

非医学问题走现有角色闲聊。不检索，不加约束。

非目标：不做通用多意图体系，不改 `packages/core-agent`，不做「意图 → 工具」路由（那是 function calling 的活）。

## 2. 核心决策：两个独立维度

判定只回答「是不是医学问题」，不回答「该怎么办」。

判定和处置是两件事，必须分开配置。合成一个开关就没法表达「只用规则判定，但仍然分流」这种组合。

**维度一：判定器模式。**

| 模式 | 行为 | 调用模型 |
| --- | --- | --- |
| `rules` | 只用规则层（第 7.3 节四类信号） | 否 |
| `rules+llm` | 规则未命中时再问一次模型 | 是，且只在未命中时 |

`rules` 必须是一等形态，不是过渡期的临时设置。它是产品的长期默认值。

**维度二：处置方式。**

| 处置 | 行为 |
| --- | --- |
| `off` | 关闭分流，行为和今天一样 |
| `block` | 阶段一：回固定话术，不进模型 |
| `route` | 阶段二：换提示词 + 检索知识库 |

**推荐组合：`rules` + `block`。** 阶段一就按这个上线。它不增加任何网络请求，判定全在本地完成。

分开的理由：两阶段的判定完全相同。分离后，阶段二上线只替换处置层，判定层、契约、测试都不动。

一个已有实现（`full-repo/ruoyi` 的 `service_api.py`）把同样的开关做成了环境变量 `AI_MEDIC_GATEKEEPER_LLM`，默认 `0`，即默认走纯规则。它的任务比我们重（要同时出四类意图、就诊人画像、检索词），所以生产上需要模型。我们的任务只有二分类，规则做得了，不要因为看到它的中控就换成模型主判。

## 3. 三条代码约束（决定门挂在哪个位置）

这三条是从现有代码里读出来的，不是假设。

**3.1 上下文提供者是并发执行的。**
`chat-orchestrator-runtime.ts` 第 444–453 行用 `Promise.all` 跑完所有 `runtimeContextProvider`。
所以不能新加一个「判定 provider」去挡住「知识库 provider」。门只能放在知识库 provider 内部，或者两边等同一个共享的判定结果。

**3.2 判定可以是异步的，只要写在 provider 里。**
`ingestRuntimeContexts` 在第 516 行，`getSystemPromptSupplement()` 在第 718 行才被调用。
provider 里 await 完判定、写进 store，到 718 行拼系统提示词时已经能读到。
这解决了一个真问题：`getSystemPromptSupplement` 是同步 getter，装不下异步判定。

**3.3 发送流程没有「短路」能力。**
`ChatOrchestratorSendOptions` 没有「不调模型」的选项，`performSend` 进去就会发请求。
所以阶段一的固定回复必须在 `chat.ts` 的发送入口拦，发生在 `runtime.ingest` 之前。
放在 provider 里只能「加内容」，停不下这次发送。

## 4. 数据流

阶段一：

```
用户发送
  -> classify(message)                    判定层，同步规则优先
  -> decision = medical
  -> 写入固定助手消息 + patch streamingMessage
  -> 结束，不进入 runtime.ingest，不调模型
```

阶段二：

```
用户发送
  -> classify(message)
  -> performSend
       -> ingestRuntimeContexts                      第 516 行
            ├─ knowledge-base provider 读判定，medical 才检索
            └─ 医学模式补充上下文
       -> getSystemPromptSupplement()                第 718 行
            └─ 按判定返回 [toolset 提示词, 医学|闲聊 提示词]
  -> 正常流式回复
```

## 5. 模块划分

| 层 | 位置 | 职责 |
| --- | --- | --- |
| 契约 | `packages/stage-ui/src/libs/intent/contract.ts` | `IntentDecision` 类型、判定版本号 |
| 判定 | `packages/stage-ui/src/libs/intent/classify.ts` | 纯函数：规则命中。可选模型兜底在后面加 |
| 状态 | `packages/stage-ui/src/stores/intent.ts` | 保存本轮判定结果，提供 memo |
| 处置 A | `packages/stage-ui/src/stores/chat.ts` 的 `ingest` | `block`：短路 + 固定话术 |
| 处置 B | `packages/stage-ui/src/stores/chat/context-providers/` | `route`：门控知识库 + 提示词切换 |

阶段一只需要前三行加处置 A。阶段二替换处置 B，前三行不动。

固定话术不入 `packages/i18n`。它不是界面文案，是产品内容，放处置 A 旁边的一个常量模块即可。

## 6. 判定结果契约

字段：

| 字段 | 取值 | 为什么需要 |
| --- | --- | --- |
| `decision` | `medical` / `chat` | 唯一被消费的字段 |
| `confidence` | 0–1 | 记录用，不参与分支判断 |
| `evidence` | 字符串数组 | 命中哪些词、走规则还是模型。调词表靠它 |
| `source` | `rule` / `vector` / `model` / `fallback` | 便于统计每层各救回多少 |
| `rewrittenQuery` | 字符串 | 检索词。规则层等于原文，模型层可以改写 |
| `classifierVersion` | 整数 | 版本一变，旧的缓存结果作废 |

`confidence` 不参与分支。原因：阈值调不稳，而漏判代价远高于误判。规则命中就直接算医学问题，模型只做增量。

`rewrittenQuery` 只有阶段二用。用户原话不是好的检索词：`「宝宝黄疸怎么看」` 拿不到多少，`「新生儿黄疸 观察 判断 就医指征」` 会召回得更好。改写跟着判定一起出，不额外花一次调用。

## 7. 判定机制：三种方法

### 7.1 判什么

不判断「意图」，判断「这句话里有没有医学内容」。

这个区别决定了实现难度：前者要理解说话人的目的，后者只需要认词和句式。

### 7.2 三层的分工

三层是递进关系，不是三选一。前一层命中就结束，不再往下走。

| 层 | 手段 | 耗时 | 调用时机 |
| --- | --- | --- | --- |
| 第一层 | 规则 | 0ms | 每次发送 |
| 第二层 | 本地向量 | 几十 ms | 第一层未命中 |
| 第三层 | 小模型 | 300–800ms | 前两层都未命中 |

任意一层给出 `medical` 就是医学问题。三层都判完且都是 `chat`，结果才是 `chat`。

层内出错不算 `chat`。超时和解析失败按第 7.9 节处理，一律 `medical`。

`rules` 模式下只有第一层运行。第二、三层只在 `rules+llm` 模式下参与。

### 7.3 第一层：规则

规则不是一张大词表，是四类信号。任一命中就算医学问题。

**前置过滤：ack 白名单。**

纯应答词直接判 `chat`，不再往下走：`好的`、`嗯`、`知道了`、`收到`、`行`、`ok`。

它不是「语义上不像医学问题」，而是它不携带信息。命中它以后跑一次检索、追问一轮，都没有意义。语音入口下这类输入占比很高。

**信号一：医学实体词。**

产后访视的领域很窄，大约三块：

| 对象 | 实体举例 |
| --- | --- |
| 产妇 | 恶露、伤口、缝线、乳房、胀奶、体温、血压、便秘、腰痛、情绪、掉头发 |
| 新生儿 | 黄疸、脐带、喂养、吃奶、吐奶、大便、小便、睡眠、体重、呼吸、哭声 |
| 医疗行为 | 吃药、用药、剂量、复查、疫苗、就诊、挂号、医嘱、化验单 |

人称词和实体词必须分开。`宝宝`、`产妇`、`她` 是人称，自己不能触发；只有实体能触发。

- 「宝宝今天特别乖」：只有人称，无实体 → 闲聊
- 「宝宝今天吃了八次奶」：人称 + 喂养实体 + 数值 → 医学

如果人称也算实体，几乎每句话都会被判成医学问题。

**信号二：疑问句式。**

`正常吗`、`能不能`、`要不要`、`怎么办`、`是不是`、`多久`、`多少`、`为什么`。

这些词单独不算，和实体共现时是强证据。

**信号三：数值加单位。**

体温 `38.5`、血压 `120/80`、黄疸 `12`、吃了 `60` 毫升、一天 `8` 次。

这个信号在产后访视里几乎零误伤。闲聊不会带生理数值。

**信号四：指代回看。**

`那要吃吗`、`这个要紧吗` 本身没有实体。如果上一轮是医学问题，且这句含指代词，就归到医学。

只用于消解指代，不用于升权。反例：上一轮是医学问题，这一轮说「哦好」，不能因为上一轮就问而判医学。

**降级规则必须配禁止降级的例外。**

每加一条降级规则（把医学降成闲聊），同时加一条禁止降级的例外。降级规则的收益是少一次检索，失误的代价是漏判。

例：加「问流程的不算医学」，会把「挂什么科」一起降下去，所以要配一条例外：命中「挂什么科/看哪个科/去哪个科」时强制医学。

没有配对的例外，就不要加这条降级规则。

### 7.4 第二层：本地向量

规则做不好「没有实体词、但明显在担心病情」的句子：

> 「我有点不放心，她今天特别没精神。」

这句话一个实体词都没有，护士都知道它是医学问题。这类只能靠语义相似度。

做法：预先攒 30–50 条标注好的问句做锚点，一半医学、一半闲聊。算相似度取最近邻。`@xsai/embed` 和 transformers 已在依赖里，本地跑不花钱。

### 7.5 第三层：小模型

只在前两层都没命中时调用，所以调用率可能只有 20–30%。成本可以忽略，延迟可以接受。

问法有讲究。不要问「这是医学问题吗」。给 6–10 个例句，两个标签，并要求输出了哪个词让它这么判。

要依据词不是为了可解释性。同样输入跑一段时间后，把高频依据词搬进第一层词表，模型的使用率就会降下去。

同一次调用顺带要一个改写后的检索词（`rewrittenQuery`）。模型已经在读这条消息，多说一句不要钱。阶段二拿它去查知识库，比原话召回得好。

### 7.6 判例

| 句子 | 命中 | 结论 |
| --- | --- | --- |
| 宝宝黄疸怎么看 | 实体「黄疸」+ 疑问式 | 医学 |
| 我今天恶露比昨天多 | 实体「恶露」 | 医学 |
| 体温 38.5，正常吗 | 数值单位 + 实体 + 疑问式 | 医学 |
| 能不能洗头 | 疑问式，无实体 | 拿不准，交第二层 |
| 宝宝今天特别乖 | 只有人称 | 闲聊 |
| 好累啊 | 无 | 闲聊 |
| 那要吃吗 | 指代 + 上轮医学 | 医学 |
| 她今天特别没精神 | 无实体 | 第一层漏，交第二层 |

最后两行是「为什么需要后两层」的全部理由。

### 7.7 迭代办法

每条判定打一条日志：原文、`decision`、`evidence`、`source`。

然后按这个循环收敛：

1. 攒 100–200 条真实问句，人工标注「该不该查库」。
2. 每个错例不是调阈值，而是变成一条规则，或者一个反例排除。
3. 词表不再有新增错例时，第一层收敛。
4. 第一层收敛后仍有稳定漏判，再上第二层。

### 7.8 落地顺序

顺序是：规则 → 看漏什么 → 再决定要不要向量或模型。

理由：产后访视的医学话题边界窄，高频句式重复度高。先用规则跑一两天真实对话，把漏掉的句子逐条补成规则，很可能补到 20–30 条就饱和。那时第二、三层根本不用上。

不要一开始就把三层都建起来。

### 7.9 判定失败时的行为

判定层有三种失败：模型超时、输出解析不出来、模型不可用。

三种一律返回 `medical`，`source` 记为 `fallback`。

这不是保守，是两类错误代价不对称的直接推论（见第 1 节）。解析失败时把它当成闲聊，等于让最没把握的一类输入走最没有保护的那条路。

具体约定：

1. 解析失败不重试。解析失败说明输出形状不对，重试大概率还是一样。降级更快。
2. 判定有独立超时，超时即 `medical`，不等模型。这个超时要比知识库检索的 3 秒短，否则判定成了整条链路的瓶颈。
3. 失败必须留痕。看不到 `fallback` 的占比，就不知道模型在抖还是在正常工作。

## 8. 时序安全：不要用全局布尔

不能用 `stores.intent.isMedical` 这种全局开关。

发送有队列（`QueuedSend`）、有 generation 作废、还有 WebSocket 来源的发送。
全局布尔会让相邻两条消息串味：第二条的判定覆盖第一条，第一条的处置用到第二条的结果。

判定结果必须绑定到「这次发送」：按消息内容加会话 id 做键，或者直接把结果随上下文消息一起传下去。取用后就丢弃。

## 9. 阶段一的落地要点

1. 固定回复走正常助手消息写入路径。保留 `id`、`createdAt`，这样历史、云同步、语音合成都能正常工作。
2. 不进模型，所以不产生 LLM 请求日志和计费。消息上要留可辨识标记，避免它看起来像模型自己说的。
3. 必须留出口。用户补充细节后要能进入正常流程。不要做成一堵墙。

第 3 点是产品要求，不是技术细节：患者说「我出血很多」被固定话术挡回来，本身就是医疗风险。

## 10. 阶段二的落地要点

1. 提示词拼成两段。拼接顺序是 `[toolset 提示词, 模式提示词]`，冲突时模式提示词优先，并在文本里写明「以下约束优先于上面的通用说明」。
2. 知识库门控放在 `createKnowledgeBaseContext` 开头：非医学问题直接 `return null`。
3. 检索失败时的策略要分叉。医学问题不能静默降级成模型自由发挥，必须明确说「这个我不好确定，建议问医生」。闲聊问题静默继续。
4. 相似度阈值先实测再定。现在 `scoreThreshold` 默认是 0，等于全收，这可能是当前问题的来源之一。
5. 分流不能污染上下文。医学回合注入的内容（知识库记录、医学模式补充）必须在下一个闲聊回合开始前清掉，用固定的 `contextId` 覆盖写，而不是追加。否则闲聊回合会带着上一轮的病历记录说话，语气和内容都被拉偏。

## 11. 从阶段一到阶段二

| 动作 | 对象 |
| --- | --- |
| 保留 | 契约、判定层、状态层、策略开关 |
| 删除 | 短路分支、固定话术常量 |
| 新增 | 两段提示词、知识库门控、失败策略分叉 |

判定层零改动。这是第 2 节那个决策的全部价值。

## 12. 观测与验收

每次发送打一条结构化日志：原文摘要、`decision`、`evidence`、`source`、耗时。

验收需要一份标注集：100–200 条真实患者问句，人工标注「该不该查库」。指标两个：

- 漏判率：医学问题被判成闲聊。阶段一必须盯这个。
- 误判率：闲聊被判成医学问题。阶段二盯这个，因为它影响体感。

没有标注集，词表和阈值只能靠感觉调，换成模型后也无法证明变好了。

## 13. 已知取舍

| 取舍 | 结论 |
| --- | --- |
| 拿不准时走哪边 | 走医学。多一次严谨措辞，比漏判安全 |
| 语音输入 | ASR 文本缺标点、有错字，规则词表要单独调 |
| vLLM 上的 Qwen3-8B | 结构化输出不如 DeepSeek 稳。判定失败要有兜底值 |
| 前端持有 Key | 现有取舍。走模型判定会多一次外部调用，量小可接受 |

## 14. 不做的事

1. 不建通用意图体系。这条路上只关心「医学」和「非医学」。
2. 不改 `core-agent`。三个挂点都在 `stage-ui` 和 `stage-web` 内。
3. 不把判定结果写进系统提示词当指令。它是上下文事实，风险路径由程序直接走。

## 15. 实施步骤

四个阶段。每个阶段都能停下来，停在原地也是可用的状态。

| 阶段 | 判定器 | 处置 | 线上行为 | 新增依赖 |
| --- | --- | --- | --- | --- |
| A 地基 | `rules` | `off` | 不变 | 无 |
| B 阶段一 | `rules` | `block` | 医学问题回固定话术 | 无 |
| C 阶段二 | `rules` | `route` | 医学问题换提示词并检索 | 无 |
| D 收敛 | 可选 `rules+llm` | 不变 | 不变 | 需要时才加 |

没有一步需要新依赖。`rules` 加 `block` 全部是本地计算。

### 15.1 阶段 A：地基

目标：把判定能力做出来，但不接进任何流程。可以单独合并。

**A1 契约**

- 位置：新增 `packages/stage-ui/src/libs/intent/contract.ts`。
- 内容：`IntentDecision`（第 6 节的字段）、`IntentSource`、`CLASSIFIER_VERSION`。
- 验收：`pnpm -F @proj-airi/stage-ui typecheck` 通过。
- 影响：无运行时行为。

**A2 词表**

- 位置：新增 `packages/stage-ui/src/libs/intent/lexicon.ts`。
- 内容：四块数据。ack 白名单、医学实体（产妇、新生儿、医疗行为）、疑问句式、禁止降级例外。
- 约定：只放数据，不放逻辑。词表要能单独 review。
- 验收：数据文件不写测试。

**A3 规则判定**

- 位置：新增 `packages/stage-ui/src/libs/intent/classify.ts`。
- 签名：`matchRules(input) -> IntentDecision`，同步纯函数。
- 输入：`{ message, previousDecision? }`。`previousDecision` 只给指代回看用。
- 禁止：不 import store，不 import fetch，不读环境变量。
- 顺序：ack 白名单，实体，疑问式共现，数值单位，指代回看，降级例外。
- 验收：A4 的测试。

**A4 判例测试**

- 位置：新增 `packages/stage-ui/src/libs/intent/classify.test.ts`。
- 内容：第 7.6 节 8 条判例，加 ack 5 条、指代 2 条、降级例外 2 条。表驱动。
- 运行：`pnpm run test-ui:run`。根 `vitest.config.ts` 的 `projects` 不含 stage-ui，直接跑 `vitest run` 找不到用例。
- 验收：全部通过。每条用例连 `evidence` 一起断言，否则改了词表不知道哪条规则在起作用。

**A5 开关**

- 位置：新增 `libs/intent/config.ts`，并在 `apps/stage-web/.env.example` 补两个变量。
- 变量：`VITE_MEDICAL_GATE_CLASSIFIER`（`rules` / `rules+llm`）、`VITE_MEDICAL_GATE_MODE`（`off` / `block` / `route`）。

- 取舍：构建期变量，改值要重新构建。运行时切换要改成 settings store 存 localStorage。见 15.5 第 1 条。
- 验收：默认配置下线上行为不变。

### 15.2 阶段 B：阶段一上线

目标：医学问题回固定话术。上线后开始产生判定日志。

**B1 判定状态**

- 位置：新增 `packages/stage-ui/src/stores/intent.ts`。
- 要求：按会话 id 加消息内容做键，同一个键返回同一个 promise。取用后清理。
- 禁止：全局布尔。原因见第 8 节。
- 验收：单测覆盖两条消息并发、结果不串味。

**B2 发送前短路**

- 位置：`packages/stage-ui/src/stores/chat.ts` 的 `ingest`（约第 351 行）。
- 逻辑：`mode` 为 `block` 且判定为 `medical` 时，写用户消息、写固定助手消息、patch `streamingMessage`，**不调用 `runtime.ingest`**。
- 理由：第 3.3 节。发送流程没有短路能力，只能在入口拦。
- 固定话术：新增 `libs/intent/replies.ts`。不放进 `packages/i18n`，它是产品内容，不是界面文案。
- 消息标记：助手消息上留一个可辨识字段。见第 9 节第 2 条。
- 出口：固定话术之后要能继续。用户补充细节，下一次发送照常进流程。不要在 store 里留「已拒绝」状态。
- 验收：手动对话。请求日志和计费无新增。历史、云同步、语音合成正常。

**B3 判定日志**

- 位置：新增 `libs/intent/observability.ts`。
- 字段：消息摘要、`decision`、`evidence`、`source`、耗时、`classifierVersion`。
- 出口：开发期打 console，加一个可导出的数组。不做上报。
- 验收：跑一轮对话，能导出每一条判定。

阶段一不要停留太久。挡住真实医学问题本身是风险。B 到 C 的间隔按周算，不按月算。

### 15.3 阶段 C：阶段二上线

目标：医学问题换提示词并查知识库。前置条件：B3 的日志已经攒够。

**C1 两段提示词**

- 位置：新增 `libs/intent/prompts.ts`，改 `chat.ts` 的 `getSystemPromptSupplement`（第 298 行）。
- 拼接：`[toolset 提示词, 模式提示词]`，模式在后，文本里写明「以下约束优先」。
- 验收：闲聊回合的系统提示词里没有医学约束。

**C2 知识库门控**

- 位置：`packages/stage-ui/src/stores/chat/context-providers/knowledge-base.ts` 的 `createKnowledgeBaseContext` 开头。
- 逻辑：非医学直接 `return null`。医学用 `rewrittenQuery` 查，不用原话。
- 验收：Network 面板确认闲聊回合不发检索请求。

**C3 失败策略分叉**

- 位置：同上。
- 逻辑：医学问题检索失败时，返回的上下文里带一条明确的兜底要求，并给出字面话术。闲聊失败不注入任何东西。
- 理由：第 10 节第 3 条。8B 模型对「请不要编造」不敏感，给现成句子更有效。
- 验收：改错知识库地址后，医学问题回「我确定不了，建议问医生」，闲聊无感。

**C4 上下文清理**

- 位置：同上，或 `chat.ts` 的发送入口。
- 逻辑：闲聊回合开始前，用固定 `contextId` 覆盖医学回合注入的内容。
- 理由：第 10 节第 5 条。
- 验收：医学问一句再闲聊，prompt 里没有上一轮的记录。

### 15.4 阶段 D：按数据收敛

不加新功能。按第 12 节的两个指标改词表。

1. 攒标注集。从判定日志抽 100–200 条真实问句，人工标「该不该查库」。
2. 只改 `lexicon.ts`。每个错例变成一条规则，或者一条例外。
3. 手动加 `CLASSIFIER_VERSION`，让旧缓存失效。
4. 第一层补到不再有新增错例，再考虑 `rules+llm`。判断依据是 `source` 的分布，不是感觉。

### 15.5 开始前要定的两件事

1. **开关放哪。** 构建期环境变量简单，改值要重新构建。运行时 settings 灵活，要写持久化和设置页。阶段一建议前者，阶段二之前再定。
2. **固定话术的措辞。** 第 9 节第 3 条要求留出口。话术除了「我暂时回答不了医学问题」，必须带一句让人能继续说的话。这一句决定患者是继续描述，还是直接关掉页面。

### 15.6 顺序的理由

1. A 不接流程，可以单独合并、单独 review。
2. B 一上线就有日志。日志是后面所有决定的输入。
3. C 的需求要靠日志判断。没有日志就做 C，等于在没有数据时猜。
4. D 不是阶段，是长期循环。

每做完一个阶段停一下。不要连着做下一个。
