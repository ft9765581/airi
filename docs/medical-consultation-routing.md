标签：开发中 · 总设计 · 医疗咨询分流

## 1. 目标与范围

用户提出医疗问题后，AIRI 给出受约束的医疗咨询回答，不再统一回复“暂时回答不了”。普通聊天保持现有体验。急症信号优先得到明确的就医指引。

第一版包含：逐轮分流、医疗咨询提示词、多轮追问、失败兜底、聊天分支标识、单条试跑和批量评测。医疗轮次可以引用知识库：每条知识库连接在设置页选择服务常规聊天还是医疗咨询，医疗分支只读后者，检索结果作为本轮上下文随提示词发送，检索失败不影响回答（`docs/fork-changes.md` 第 21 节）。第一版不提供诊断或处方，不引入通用工作流编辑器，也不把 Devtools 的提示词草稿直接用于正式聊天。

“医疗咨询助手”是产品角色，不代表执业医生。它可以解释一般知识、整理症状和建议就医时机。它不能声称已诊断、保证安全，或根据不足的信息给出具体用药方案。

现有卡片的系统消息会写入会话历史。医疗轮次不能只把医疗提示词追加到原系统消息末尾，否则两套人格规则可能冲突。实现时应在**本轮发送给模型的消息副本**中替换角色人格部分，保留必要的通用格式约束；不要永久改写会话里的原系统消息。`core-agent` 需要能替换提示词的逐轮接口，不能复用仅追加的 `getSystemPromptSupplement`。普通聊天继续使用原角色卡提示词。

## 3. 逐轮流程

```text
用户消息（文本或语音转写）
  → 进入当前会话的发送队列
  → 读取当前消息和必要的同会话上文
  → 先检查当前消息及直接相关上文中的急症信号
      → 急症：写入明确的急诊指引，结束本轮
  → 无急症时识别意图
      → 医疗：选择 medical agent，生成医疗咨询回答
      → 非医疗：运行原普通聊天流程
      → 识别失败：写入安全兜底，记录失败原因
  → 保存本轮分支、回答和诊断元数据
```

每条消息独立判断。上一轮为医疗咨询时，当前的“那这个呢”“需要复查吗”等追问须带上同会话上文判断；“晚安”一类明确转题消息回到普通聊天。不要把整个会话永久锁定为医疗模式。

分类输入应保留上文的角色和先后顺序，至少包含最近的用户问题与助手回答。当前 `classifyWithModel()` 只接收无角色标记的字符串数组，不能直接承担完整的多轮判断。急症检查以当前消息为主；仅当当前消息明确指向紧邻的医疗上文时才继承其中的危险信号，不因更早的历史描述反复触发急症。

正式聊天只使用通过第 7 节验收的分类策略。现有 `rules`、`model`、`compare` 是评测模式，不作为用户设置；`compare` 不能直接决定正式路由。Embedding 的测试页设计与后续组合策略见 [intent-routing.md](./intent-routing.md) 第 4—8 节。两者目前仅作候选，未通过验收前不接管正式路由。若识别策略尚未达标，保留固定医疗回复，不启用医疗生成。

急症判断优先于普通医疗生成。急症分支继续复用现有明确的急诊指引，并能识别上下文中的危险信号。普通医疗回答不能覆盖急症指引。

医疗 agent 缺失或 `enabled: false` 时，不发起医疗生成，继续使用现有固定医疗回复。提示词为空或所选模型不可用时，也使用固定医疗回复，并记录具体原因。不得静默落回普通人格回答医疗问题。识别服务失败时使用独立的安全兜底；失败不是“已识别为医疗”。

当前 `chat.ts` 在 `runtime.ingest()` 入队前执行医疗拦截。改造时，各入口先入同一队列，再在出队后的消息快照上路由。同一会话的并发消息按队列顺序执行，第二条消息可看到第一条回答。清空、删除或取消会话时，进行中的咨询不得把回答写回失效会话。重试时重新执行该轮路由，并更新对应的分支记录。

当前 `executeSend()` 在拦截前要求普通聊天模型已配置，`ChatOrchestratorSendOptions` 也要求入队时传入模型和 Provider。改造时需同时调整这两个契约：发送入口先传入可排队的用户输入，出队后再按分支获取模型。急症、固定回复和识别失败兜底不能依赖模型配置。生成失败后只写一条兜底助手消息，避免同时留下错误消息和兜底消息。

## 4. 配置与提示词

首版将医疗 agent 定义在角色卡：

```json
{
  "extensions": {
    "airi": {
      "agents": {
        "medical": {
          "enabled": true,
          "prompt": "医疗咨询助手的系统提示词"
        }
      }
    }
  }
}
```

`enabled` 必须显式为 `true` 才启用。此配置归角色卡所有，切换角色卡后使用新角色卡的医疗 agent。没有配置时继续使用现有固定医疗回复，避免旧卡片因升级自动开启医疗生成。正式启用前，必须修复角色卡包导入导出的 `agents` 丢失问题。

角色卡开关只表示该角色愿意使用医疗 agent。正式环境还须通过第 7 节门槛并完成多轮路由，才启用医疗生成。B 阶段的具体接线步骤见 [medical-consultation-routing-stage-b.md](./medical-consultation-routing-stage-b.md)。

`agents.medical` 当前只是提示词与启用标记的存储槽，不会自动执行 `SKILL.md`，也没有独立的工具或模型配置。第一版不把它当成可执行技能包；运行时必须显式读取并选择这个 agent。

### 知识库

知识库连接在设置页（`packages/stage-pages/src/pages/settings/knowledge-base/`）配置，每条连接有一个「在医疗咨询流程中使用」的勾选，决定它服务哪条流程：

设置页提供「添加医疗知识库」入口：点它预填本部署的检索地址并勾选医疗分支，只留知识库 ID 给人填。

| 勾选 | 谁读它 | 何时检索 |
| --- | --- | --- |
| 不勾选（`scope: 'chat'`） | 常规聊天的上下文提供者 | 每个普通聊天轮次 |
| 勾选（`scope: 'medical'`） | 医疗分支的路由代码 | 只有本轮被判为医疗、且角色卡有可用 `agents.medical` 时 |

医疗轮次是隔离轮次，读不到运行时上下文提供者，所以检索由路由发起，结果放在 `TurnRouteResult.contextMessages`，作为上下文块注入，而不是拼进系统提示词。固定回复、急症指引和兜底三种分支都不发起检索；检索失败只让本轮少一份参考。

医疗提示词由两部分组成：应用维护的**行为约束**，以及角色卡的**人格与表达方式**。发送时先放应用约束，再放角色卡提示词；导入角色卡时校验 `agents.medical` 的字段类型。两者冲突时按应用约束处理，且急症由路由代码先行处理，不能只依赖提示词。行为约束包括不编造检查结果、信息不足时追问、不提供具体诊断和处方。角色卡可以配置称呼、语气、回答长度和擅长的主题。分类提示词与咨询提示词分开保存，不混用。

每轮发送前计算有效提示词的内容摘要，并随路由记录保存。Devtools 编辑的草稿只用于试跑；只有经过评测并保存到角色卡的配置才参与正式聊天。第一版医疗咨询使用当前会话已选模型；单独选医疗模型可以留到有实际需求时增加。

## 5. 回答与数据契约

| 输出 | 首版要求 |
| --- | --- |
| 路由结果 | 在 `core-agent` 拥有的会话消息契约中定义本轮元数据：`route`（`urgent`、`medical`、`chat`、`fallback`）、分类来源、失败原因、耗时和提示词摘要。 |
| 医疗回答 | 先回应问题；信息不足时只问最关键的补充问题；必要时说明就医时机。避免每条都重复长免责声明。 |
| 用户可见状态 | 医疗生成的消息显示“医疗咨询”标识；急症指引使用醒目的独立样式；普通聊天不显示医疗标识。 |
| 保存与同步 | 用户消息、助手消息按原有会话机制保存。分支元数据附在该轮助手消息，保存在本地会话；现有云同步只推送 `role` 和 `content`，跨设备恢复暂不显示分支标识。控制台日志和评测记录不存医疗正文。 |
| 失败 | 分类失败、医疗 agent 未启用、模型失败分别记录原因。用户只看到可理解的兜底文案和下一步建议。 |

模型回答仍需按现有消息流写入，支持流式显示、取消和重试。分类器只决定路由，不负责生成医疗回答。医疗回答不能把分类器的 JSON 当作用户可见文字。会话元数据在消息投影到模型输入时必须移除。

## 6. 页面与交互

### 6.1 用户设置：医疗咨询

入口放在角色卡设置附近，因为医疗 agent 随角色卡保存。首版页面只需四块：

| 区块 | 内容 |
| --- | --- |
| 状态 | 开关、当前角色卡、当前咨询模型、缺少配置时的原因。 |
| 人格 | 医疗助手名称、语气、范围；高级项可编辑 `agents.medical.prompt`。应用行为约束只读展示。 |
| 预览 | 一条示例问题和生成结果；清楚标明预览不写入聊天会话。 |
| 保存 | 保存后显示生效状态；离开前提示未保存的改动。 |

设置页不展示分类器的 JSON、证据码或整批评测表。开关关闭时，现有医疗固定回复继续生效。新旧两条固定回复与新增用户文案只维护中文，核对用词与现有医疗提示一致；本阶段不做多语言翻译。

### 6.2 聊天界面

医疗回答使用轻量标签，避免让用户误以为对话对象突然变成另一位真人医生。急症卡片突出“立即就医”动作；保持文字可读，不只依靠颜色。点击消息的详情入口可查看“本轮使用医疗咨询”这一事实，无需显示完整内部提示词。

### 6.3 Devtools：分流实验台

保留开发环境入口 `intent-routing`。先按 [识别实验计划](./intent-routing.md) 完成同一页面的分类对照；阶段 B 的路由和回答能力可复用后，再按工作顺序扩展页面：

1. **配置摘要**：分类模式、模型、分类提示词版本、医疗 agent 启用状态、咨询提示词版本。草稿和已生效配置明显区分。
2. **单轮与多轮试跑**：输入上文和当前消息；选择“只测识别”或“完整试跑”。完整试跑复用同一套路由和回答逻辑，但使用隔离的内存会话；禁用云同步、记忆写入和外部副作用工具。
3. **逐步结果**：依次显示急症检查、规则结果、模型结果、最终路由、有效提示词来源、生成回答、耗时与失败原因。失败结果不能显示为“模型判对”。
4. **批量评测**：显示医疗召回、闲聊误判、模型有效回答率、回退率、各组错例。点击错例即可填入上方试跑区，保留该样本的上文。
5. **结果追溯**：为样本集增加 `intentSampleSetVersion` 并写入 `EvaluationReport`；另记分类器版本、模型名、分类提示词摘要、咨询提示词摘要和运行时间。配置变化后将旧报告标记为“不可直接比较”。

按钮在运行期间显示进度。模型未配置或医疗 agent 未启用时，解释具体缺项。批量评测需明确请求条数及可能的模型调用次数，支持取消，并避免重复点击触发多次运行。

## 7. 评测先决条件

当前工作区已改动以下四项。阶段 A 仍需用自动化测试和真实模型报告核验，并把结果纳入可复现的评测基线：

1. `evaluate.ts` 汇总错例时把同一决策同时放进 `rules` 和 `model`；改为保留原始两侧决策。
2. 模型失败回退到 `medical`，现有命中率可能把回退计为正确；把失败与有效模型判断分开计分。
3. 评测页只读取已保存的 `config.baseUrl`，而部署默认 DeepSeek 配置只存密钥；复用 Provider 定义的默认地址解析，不硬编码另一份地址。
4. 分类请求要明确关闭 DeepSeek thinking，并校验输出长度、超时和 `finish_reason`；被截断的 JSON 计入失败原因。

复核需要上下文的标注样本。对“我有点不放心”这类缺少上文的句子，补充上文或调整标注，不用模糊标签反复调提示词。保留一组未参与调优的脱敏样本作为最终验证集。

初始发布门槛如下。当前实现的医疗咨询分支采用生成式模型分类；规则只用于前置急症判断。Embedding 或组合策略仍须单独评测，通过同一门槛后才能替换当前分类策略。先用训练样本调优，再用不少于 300 条未参与调优的脱敏样本验收。验收集至少包含 150 条医疗问题和 100 条普通聊天，并覆盖短句、就医流程及 ASR 错字。另设人工复核的急症集。下面的数字是发布目标，未达到时保持固定医疗回复，不开启医疗生成。

医疗召回率的分母是所有标为医疗的样本，只有有效分类为医疗才算命中。闲聊误判率的分母是所有标为闲聊的样本，只有有效分类为医疗才算误判。分类失败单列，仍留在前两项的分母中；不能把回退到 `medical` 计为模型命中。正式路由的急症和兜底另计，不混入模型分类指标。

每条用户消息算一次分类。若后续引入重试，失败率按最终路由结果除以用户消息数计算，另报告每次请求的失败率及重试次数。P95 从开始分类到获得有效结果或兜底为止，超时和重试都计入耗时。

| 指标 | 首版发布门槛 |
| --- | --- |
| 医疗召回率 | ≥ 95% |
| 闲聊误判率 | ≤ 5% |
| 逐轮分类失败率 | ≤ 1% |
| 急症样本命中 | 人工复核的急症测试集全部命中 |
| 分类 P95 耗时 | ≤ 2 秒；同时报告样本量和测试环境 |

这些指标验证分类和路由。另对医疗回答做人工审核：检查急症指引、虚构事实、诊断和用药建议。模型回答若不符合约束，不能仅凭分类指标开启医疗生成。

| 用例 | 预期 |
| --- | --- |
| “宝宝黄疸怎么看” | 进入医疗咨询；不再得到普通聊天回答。 |
| “宝宝今天特别乖” | 进入普通聊天。 |
| 医疗上文之后的“那这个呢” | 结合该会话上文进入医疗咨询。 |
| 医疗上文之后的“晚安” | 回到普通聊天。 |
| “大量出血，头晕” | 优先显示急诊指引，不等待医疗生成。 |
| 模型超时或返回无效格式 | 显示兜底；报告计入失败，不计为模型正确。 |
| `agents.medical.enabled` 为 `false` | 继续固定回复，不调用医疗生成模型。 |
| 角色卡导出再导入 | `agents.medical` 提示词和启用状态保持一致。 |

## 10. 首版决策与复测

### 10.1 医疗路由策略

当前医疗咨询分支采用生成式模型分类；规则只负责先行识别急症。`compare` 仍用于 Devtools 对照，不参与正式路由。模型分类失败时进入安全兜底，不把规则的普通医学词命中当成有效模型判断。Embedding 分类和组合策略是待评测的后续选择，不能直接把相似度分数当成已验证的医疗判断。

92 条训练样本上的两次探索性运行出现不同分数。第 9 节记录的一次结果是医疗召回 75.0%、闲聊误判 19.4%；另一次约为 82.1% 和 27.8%。这些结果没有形成带完整模型、提示词和请求参数的可复现报告，不能据此宣布模型已达到第 7 节门槛。阶段 A 应在固定配置下复测多次，再用独立验收集决定是否启用医疗生成。

### 10.2 就医流程的标签

`IntentScene` 表示话题，`decision` 表示处理分支；`hospital-process` 不等于 `medical`。现有 `prc-*` 组有 8 条行政流程标为 `chat`，另有“复查挂哪个科”标为 `medical`。沿用这个产品口径：需要临床判断的就医问题进入医疗咨询；停车、报销、材料、改号等行政问题走普通聊天。不要为降低误判率而改写标签。

医疗助手首版不承担院内行政流程查询。对同一话题中的两类样本分别统计错例；若将来增加院内服务路由，再为它定义单独的能力与标注。

### 10.3 超时、失败与重试

当前工作区把分类请求设为关闭 thinking、`max_tokens: 512`、超时 4000 ms，并把输出截断记录为 `fallback:truncated`。这些参数属于待核验实现，不替代阶段 A 的稳定性评测。

首版不自动重试分类。失败时立即进入安全兜底，并记录失败类型、耗时及模型配置摘要。后续若加入重试，必须重新计算第 7 节的逐轮失败率和 P95；不能只统计成功请求，或把多次请求当成多个用户问题。

### 10.4 验收数据的归属

未参与调优的验收集和独立急症集都由阶段 A 交付。当前的 92 条样本参与过调优，只能用于开发诊断。`intentSampleSetVersion` 已加入当前工作区的报告；验收集也必须有独立版本，且每份报告保存实际使用的样本集版本。
